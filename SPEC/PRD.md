## 2. 产品概述

LLM Wiki Desktop 是一款本地优先的跨平台桌面知识库应用。它帮助用户把分散的文章、网页、PDF、Office 文档、Markdown 笔记和剪贴板内容，自动整理成结构化、互相链接、可探索、可问答、可导出的 Markdown Wiki。

产品遵循 Karpathy 的 LLM Wiki 模式：原始资料保留在 Raw Sources，LLM 或 Agent 将资料编译成 Wiki 页面，Schema 定义整理规则和页面结构。与传统 RAG 的差异在于：知识不是每次提问时临时拼接，而是被持续沉淀为可阅读、可维护、可版本化的知识库。

首版采用“零门槛知识库 + Agent 增强”策略：用户可以通过简单导入获得完整知识库体验；高级用户可以接入 Claude Code、Codex、OpenClaw、Hermes 等本地 Agent CLI，执行复杂编译、Lint 修复、HTML 生成和知识维护任务。

## 3. 背景与问题

### 3.1 用户现状

个人知识管理者和研究型用户常常面对以下情况：

- 资料散落在 PDF、网页、公众号文章、PPT、Word、Excel、Markdown 和本地文件夹中。
- 普通笔记工具依赖手工整理，成本高，长期难以维护。
- RAG 工具能问答，但不擅长把知识沉淀成稳定、可编辑、可复用的页面。
- 图谱工具通常需要用户手动建节点、连线，不适合大量资料导入后的自动探索。
- AI Agent 能整理资料，但命令行门槛高，普通用户不容易获得稳定、可恢复、可视化的工作流。

### 3.2 核心问题

用户需要一个本地桌面应用，把“资料导入、知识整理、图谱探索、问答溯源、HTML 输出、版本恢复”整合成一个可靠闭环。

### 3.3 产品机会

LLM Wiki Desktop 的机会在于：

- 以 Markdown 文件夹作为长期资产，避免锁定在单一应用。
- 用 Agent/LLM 自动完成重复整理工作，降低个人知识库维护成本。
- 用知识图谱作为首个惊喜时刻，让用户一眼看到资料之间的结构。
- 用 Git 自动检查点保护用户资料和 AI 修改结果。
- 用 Skill 系统承接未来扩展，而不是把所有能力硬编码在应用中。

## 4. 产品目标

### 4.1 MVP 目标

MVP 必须让用户完成以下闭环：

1. 新建或打开一个项目。
2. 导入一批多格式资料。
3. 预览解析结果并确认编译。
4. 自动生成 Wiki 页面、索引、概览和页面链接。
5. 查看可探索的知识图谱。
6. 基于 Wiki 内容进行 Chat 问答并查看引用来源。
7. 生成单篇 HTML/知识卡片或项目级 HTML 报告。
8. 通过 Git 检查点、Lint、后台任务和通知保证过程可恢复、可维护。

### 4.2 产品原则

- **本地优先**：项目内容默认只保存在本地文件夹中。
- **文件透明**：Wiki 页面是普通 Markdown，可被 Obsidian、Git 和外部编辑器访问。
- **导入不破坏**：原始资料默认保留，导入层尽量无损。
- **AI 可控**：普通编译自动执行，高风险删除、覆盖和冲突操作需要确认。
- **图谱优先可感知**：导入后的第一价值感来自可探索、好看的知识图谱。
- **Agent 增强而非强依赖**：Agent 提供高级能力；BYOK API 可支撑临时核心流程。
- **可恢复**：AI 和批量操作必须被 Git 检查点保护。

## 5. 目标用户

### 5.1 首要用户：个人知识管理者

**画像**：长期收藏文章、PDF、网页、课程材料、项目笔记，希望降低整理成本。

**核心诉求**：

- 快速导入大量资料。
- 自动生成结构化知识库。
- 通过图谱发现主题和关系。
- 能搜索、阅读、编辑和问答。
- 不想先学习复杂 Agent CLI 或 Git。

### 5.2 次要用户：研究者

**画像**：需要整理多来源资料、追踪引用、做主题综合和对比分析。

**核心诉求**：

- 资料来源可追踪。
- 问答有引用依据。
- 能生成综合页面、对比页面和项目报告。
- 能持续维护资料变化，避免旧内容失效。

### 5.3 高级用户：AI/技术从业者

**画像**：熟悉 Claude Code、Codex 等 Agent CLI，希望把本地 Agent 接入知识库工作流。

**核心诉求**：

- 使用本地 Agent 和 Skill 执行高级整理、Lint、HTML 生成。
- 保留项目文件结构、Git 历史和可扩展能力。
- 能控制 Agent 输出和回滚结果。

## 6. 用户场景

### 6.1 从普通资料文件夹开始

用户有一个包含 PDF、Word、PPT、网页摘录和图片的资料文件夹。用户选择“打开为项目”，应用自动初始化项目结构，把文件按类型迁入 `raw/`，生成 Wiki 和图谱。用户随后在图谱中点击主题节点，进入文章阅读。

### 6.2 导入资料到已有项目

用户已有一个 LLM Wiki 项目。用户把新的文件夹拖入应用，选择“导入到当前项目”。应用复制资料、解析文本和图片、展示预览，用户确认后触发编译。

### 6.3 基于知识库提问

用户在 Chat 中询问“这些资料里关于 Agent Memory 的主要观点是什么？”。应用搜索相关 Wiki 页面，调用 Agent 或 BYOK API 生成回答，并展示引用页面。用户可将优质回答保存到 `wiki/queries/`。

### 6.4 生成可分享材料

用户打开一篇概念页面，生成美化阅读页或知识卡片；或者对整个项目生成 HTML 报告，输出到 `exports/html/`，便于阅读、归档和分享。

### 6.5 维护知识库健康

用户运行 Lint。应用先执行本地快速检查，再让 Agent 执行深度检查。发现死链、孤立页面、重复主题或来源缺失后，应用创建 Git 检查点并自动修复可处理问题；高风险修改需要用户确认。

## 7. 范围定义

### 7.1 MVP 范围

MVP 包含：

- 项目创建、打开、最近项目管理。
- 普通文件夹自动初始化为项目。
- 多格式资料导入、解析预览、确认编译。
- Wiki 自动编译与页面浏览。
- WYSIWYG 阅读/编辑切换。
- 页面级知识图谱。
- Chat 问答与引用溯源。
- Agent CLI 检测、配置、执行与日志展示。
- BYOK API 临时后备路径。
- HTML/卡片/项目报告生成。
- Git 自动检查点、合并冲突处理和恢复。
- 本地快速 Lint + Agent 深度 Lint。
- 后台任务、托盘行为、系统通知。
- 中英双语、亮色/暗色主题、更新检查。

### 7.2 非目标

PRD 仅列出当前不纳入 MVP 的内容，后续可重新评估：

- 团队协作与多人实时编辑。
- 云同步和账号系统。
- 移动端应用。
- 浏览器扩展。
- 插件市场。
- 内置复杂权限沙箱。
- 完整网页离线归档。
- 图谱中手动拖线创建关系。
- 反向链接独立面板。
- 普通搜索栏自动触发模型问答。

## 8. 核心产品流程

### 8.1 新建项目流程

1. 用户点击“新建项目”。
2. 选择项目名称、位置和项目模板。
3. 应用生成统一项目目录结构。
4. 根据模板生成 `purpose.md` 和 `schema.md`。
5. 应用初始化 Git 仓库并创建初始提交。
6. 进入 Dashboard。

### 8.2 打开普通文件夹为项目

1. 用户选择“打开为项目”。
2. 应用判断该目录是否已有项目结构。
3. 如果是普通文件夹，自动创建 `purpose.md`、`schema.md`、`raw/`、`wiki/`、`.app/`、`exports/`。
4. 应用按文件类型移动原文件到对应目录。
5. 同名或疑似重复文件自动重命名并记录冲突报告。
6. 初始化 Git 检查点。
7. 展示导入解析预览。

### 8.3 导入到当前项目

1. 用户点击“导入”或拖拽文件/文件夹。
2. 选择“导入到当前项目”。
3. 应用复制资料到 `raw/sources/` 或 `raw/assets/`。
4. 提取文本、图片、元数据到 `raw/extracted/`。
5. 展示解析预览。
6. 用户确认后触发编译。

### 8.4 Wiki 编译流程

1. 应用创建 Git 检查点。
2. 选择 Agent CLI 或 BYOK API。
3. 编译器读取 `purpose.md`、`schema.md`、`raw/extracted/` 和现有 `wiki/`。
4. 生成或更新 Wiki 页面、`index.md`、`overview.md`、`log.md`。
5. 应用检测是否存在人工修改冲突。
6. 无冲突自动合并；有冲突展示 Markdown Diff。
7. 成功后提交 Git 版本并刷新 UI。

### 8.5 图谱探索流程

1. 应用读取 Wiki 页面和 `[[wikilinks]]`。
2. 结合多信号关联度模型生成页面级图谱。
3. 展示节点、边、页面类型颜色和社区聚类。
4. 用户点击节点进入文章。
5. 应用缓存布局，后续秒级打开。

### 8.6 Chat 问答流程

1. 用户进入 Chat。
2. 输入自然语言问题。
3. 应用搜索相关 Wiki 页面。
4. Agent CLI 或 BYOK API 生成回答。
5. 回答展示引用来源。
6. 用户可保存回答到 `wiki/queries/`。

### 8.7 Lint 修复流程

1. 用户点击运行 Lint。
2. 应用执行本地快速 Lint。
3. 可选执行 Agent 深度 Lint。
4. 展示问题列表与修复计划。
5. 应用创建 Git 检查点。
6. 自动修复可处理问题。
7. 删除、覆盖和冲突操作请求用户确认。
8. 成功后提交结果。

## 10. 信息架构

应用主导航包含：

- Dashboard
- 文件树 / 文章浏览
- Chat 问答
- 知识图谱
- Agent 面板
- 导入
- Lint
- 设置

右侧面板根据主内容切换：

- 文章页：元数据、引用来源、相关文章。
- Chat：引用来源、保存到 Wiki。
- Agent 面板：实时输出、任务状态、错误日志。
- Diff 页面：冲突详情、合并选项。
- HTML 预览：预览、导出位置、重新生成。

## 11. 非功能需求

### 11.1 性能

- 面向 200-500 篇 Wiki 页面保持流畅。
- 图谱缓存后秒级打开。
- 搜索、文章打开、文件树切换应接近即时响应。
- 长任务必须进入后台任务系统，不阻塞 UI。

### 11.2 可靠性

- 任何批量修改前必须有 Git 检查点。
- Agent 或 BYOK 编译失败不能破坏已有 Wiki。
- 导入失败需标记具体文件和错误原因。
- 冲突、失败和自动重命名需记录在 `.app/import-conflicts.json` 或任务日志中。

### 11.3 安全与隐私

- 项目内容默认只保存在本地。
- API Key 使用系统钥匙串或凭据管理器。
- 应用不静默安装 Agent 或执行安装命令。
- Agent 执行继承 CLI 自身权限与沙箱机制。

### 11.4 兼容性

- 目录结构兼容 LLM Wiki、`nashsu/llm_wiki` 和 Obsidian。
- Markdown 文件可由外部编辑器修改。
- 路径处理必须跨平台，内部统一使用正斜杠。
- 必须安全处理 Unicode 和 CJK 文件名。

### 11.5 可维护性

- 项目状态使用 Markdown 和 JSON，不引入数据库。
- Skill 系统采用文件夹 + `SKILL.md` 约定。
- HTML 模板与项目模板职责分离。
- 本地规则与 Agent 判断类规则分层。

## 12. 成功指标

### 12.1 MVP 验收指标

- 小型多格式资料包可完成导入、预览、编译、图谱、问答、HTML 导出。
- 当前 `wiki/` 样本项目可打开，文件树、搜索、图谱可用。
- Agent CLI 和 BYOK API 两条路径均能完成基础编译。
- Lint 可发现并修复至少一类本地确定性问题和一类 Agent 深度问题。
- Git 检查点可用于回滚一次 Agent 自动修改。
- 后台任务关闭窗口后仍可继续，并在完成后发出系统通知。

### 12.2 用户体验指标

- 新用户从打开应用到看到第一个图谱，不需要理解 Git 或 Agent CLI。
- 导入确认前，用户能看懂哪些文件解析成功、哪些失败。
- 用户能明确区分“打开为项目”和“导入到当前项目”。
- 冲突发生时，用户能看到差异并做出选择。

## 14. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 多格式解析质量不稳定 | 导入体验变差，Wiki 质量下降 | 解析预览明确提示失败和缺失；导入层只承诺无损保留 |
| Agent 输出覆盖人工修改 | 用户失去信任 | Git 检查点 + 基线检测 + Markdown Diff |
| 图谱大项目性能不足 | 核心惊喜时刻受损 | 首版限定 200-500 页面目标；布局缓存；后台构建 |
| BYOK 与 Agent 能力边界不清 | 用户困惑 | UI 明确标识当前执行路径和高级功能依赖 Agent |
| 自动修复误删内容 | 数据风险 | 高风险操作必须确认；修复前检查点；可回滚 |
| 项目结构对普通用户过重 | 首次体验复杂 | 默认隐藏内部细节，以 Dashboard 和导入流程承接 |
