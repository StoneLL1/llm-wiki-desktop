# 踩坑清单 (gotchas.txt)

> 记录反复出现的错误、隐蔽陷阱和"踩过一次就别再踩"的坑。
> 每条记录：现象 — 根因 — 规避做法。遇到同类问题先查这里。

[2026-06-21] 现象 — BYOK 密钥边界测试「断言 settings.json 不含 sk-ant」通过，但实际是空真断言。 — 根因 — 测试从未调用 secret_service.set(...) 存任何 key，就断言「文件不含 key」——当然不含，因为根本没存过。一个未来把 key 写进 settings.json 的回归照样通过此测试。 — 规避做法 — 测密钥隔离时**先 set 一个真实 key 到 SecretService，再断言**(a) store 能 get 回该 key，(b) 持久化的 settings.json 不含任何秘密形态（不只查单一前缀 `sk-ant`，还要查 `api_key/apikey/authorization/bearer/token` 等任意大小写，因为契约是「无任何秘密材料」而非「无这一种 key」）。
[2026-06-21] 现象 — import 集成测试 `preview.summary.archived_files` 恒为 0。 — 根因 — 测试把源文件直接 staging 到 `raw/sources/`（项目内），preview_import 的 scan_existing 递归扫 raw/ 把刚写的源文件自身按 hash 命中→判为 ExactDuplicate→archived_files 不增。同理 extract_text 写到 raw/extracted/ 的提取文本若与源同内容也会被当成重复。 — 规避做法 — import 测试的源文件必须 staging 在**项目根之外**（真实导入流程也是源来自别处）；若要同时测提取，先 preview+confirm（归档源）再 extract，或 extract 到项目外（但 extract_text 要求 output 在项目内，故改为先 confirm 再 extract）。
[2026-06-21] 现象 — 复制样本 wiki 切片到 temp 项目后，逐路径断言「每页必在扫描结果」对 `_archive/entities/codex-openai.md` 失败（文件在磁盘但不在 tree.pages）。 — 根因 — copy helper 同时用「相对 src_root 的 rel」做两件事：记录项目相对路径 AND `dst.join(rel)` 拼目标；但 dst 是当前已下降的子目录，join 全 rel 导致双嵌套（文件落 `_archive/entities/_archive/entities/...`），记录的路径与实际落盘位置不符。 — 规避做法 — 递归复制目录树时 src 与 current_dst **lockstep 下降**（每层只 join 当前 entry 名），项目相对路径从「最终目标 dest.strip_prefix(wiki_dir)」反推，不要用相对源根的 rel 同时驱动记录与拼接。
[2026-06-21] 现象 — 测试断言 CSV 提取状态为 `Unsupported` 失败（实际 `Extracted`）。 — 根因 — 先入为主以为「MVP 无 CSV 解析器」，但 ExtractionService 的 extract_text 对 Markdown|Text|**Csv** 共用同一文本提取分支，CSV 作为原始文本被提取。把 fixture/QA 文档/测试都标成「CSV 是 parser 缺口」与真实行为不符。 — 规避做法 — 新增格式断言前先读 extract_text 的实际分支表，或跑一次看实际 status；fixture 矩阵与 Rust 行为必须对齐，否则 fixture 自洽测试过但描述误导。MVP 真正的 parser 缺口是 pdf/docx/pptx/xlsx/image。

[2026-06-21] 现象 — claude/codex Agent 在 App 内报 "program not found"，但新开终端 `where claude` 成功。 — 根因 — 双层：(1) GUI 启动 / IDE shell 继承的 App 进程 PATH 可能不含 `%APPDATA%\npm`，与全新终端不同，故 App 内 `where claude` 可能直接失败；(2) 即便 `where` 成功，Windows 的 `where claude` 把**无扩展名 bash shim 排第一**、`claude.cmd` 排后面，而 Rust `Command::new(<无扩展名路径>)` 走 `CreateProcess` 无法执行该 shim → spawn 失败 → detect 判 Missing。 — 规避做法 — Windows 上 spawn 由 npm 全局装的 CLI（claude/codex）前必须先解析到可执行文件：(a) `find_executable` 在 `where` 输出里**优先选 `.cmd`/`.bat`/`.exe` 行**而非盲取第一行；(b) 加 `%APPDATA%\npm` 直接探测兜底，应对 App 进程 PATH 缺失该目录；(c) 用 `resolve_program(bare_name)` 把裸名解析成全路径再传 `Command::new`，已有路径/非 Windows 原样返回。不要把 `where` 第一行当权威。
[2026-06-20] 现象 — 构建后大量按钮（顶栏切换项目、工作区头部每视图主/次操作、左栏最近页面、Wiki 星标）点击完全无反应、控制台无报错、无 IPC reject。 — 根因 — 这些 `<button>` 在 shell 脚手架期只写了样式+标签，**从未接 onClick**（React 合成事件走根委托，`btn.onclick` 检测不可靠，须读源码确认），既不是 IPC 报错也不是 hasTauri 静默 return。 — 规避做法 — 新增可点击元素后，用 `grep '<button' src/**/*.tsx | 检查每个开标签后 6 行内有无 onClick` 扫描无 handler 的死按钮；浏览器态（无 __TAURI_INTERNALS__）所有调用 Tauri 的按钮必须经 requireTauri() 守卫弹 toast，禁止静默 no-op（否则用户只看到「没反应」无法定位）。
[2026-06-20] 现象 — project_service 初始化 bookmarks.json 写成对象 `{ "bookmarks": [] }，但 search_service.load_bookmarks 反序列化为 `Vec<String>`（数组），二者格式不一致。 — 根因 — 新项目首次创建时写入对象，reader 解析失败 `unwrap_or_default()` 静默回退空集，导致**书签永不持久化**（toggle 写数组、scan 读数组，但初始文件是对象 → 首次 load 永远空）。 — 规避做法 — JSON 状态文件的 writer 和 reader 格式必须逐字对齐；新增持久字段时先固定一种格式（此处统一为顶层数组 `[]`），让 init/write/read 三处一致，并加 round-trip 单测（toggle→reload→scan 断言 bookmarked）。
[2026-06-20] `extract_wikilinks` 返回 `"target-a]"` 而非 `"target-a"`（尾部多一个 `]`）— 根因：深度计数器在遇到第二个 `]` 时降到 0 并 break，此时 `j` 指向第二个 `]`，但 `body[start..j]` 包含了第一个 `]`（位于 j-1）— 规避：切片用 `body[start..j.saturating_sub(1)]` 排除第一个闭合括号。该 bug 被 alias 管道拆分 (`split('|')`) 和 `#` 锚点拆分意外兜底，仅纯 `[[target]]` 形式暴露。
[2026-06-20] `snippet_for_query` 测试断言 snippet 包含完整查询词失败 — 根因：`start + radius` 可能小于 `start + query.len()`，截断匹配词尾 — 规避：`snippet_end = (char_end).min(start + radius.max(query.len()))`，确保片段至少覆盖完整匹配词。
[2026-06-20] `GlobalSettingsFile` 派生 `Default` 导致 `language` 为空串而非 `"en"` — 根因：`#[serde(default = "default_language")]` 仅影响反序列化，不影响 `Default` trait — 规避：手动写 `impl Default for GlobalSettingsFile`，调用 `default_language()` 赋值。
[2026-06-20] lint_service `check_index_drift` 与 DeadLink 检测使用不一致的链接解析方式 — IndexDrift 用精确路径匹配 (`existing.iter().any(|p| *p == target)`)，DeadLink 用 `build_target_lookup`（文件 stem + title + alias）— 规避：统一使用 `build_target_lookup` 解析，`check_index_drift` 改为接收 `&HashMap<String, String>` 并用 `lookup.contains_key()`。
[2026-06-20] Windows NTFS 上两个仅大小写不同的文件（`React.md` / `react.md`）无法共存，`detects_duplicate_filename_and_path_case` 测试的 PathCase 断言失败 — 根因：NTFS 大小写保留但不敏感，第二次 `fs::write` 覆盖第一个 — 规避：PathCase 断言用 `cfg!(not(target_os = "windows"))` 条件化。
[2026-06-20] 测试中 `extract_text` / `extract_batch` 传入 `root` 作为 output_dir，但 `write_extracted_text` 校验相对路径以 `raw/extracted/` 开头 — 根因：测试未创建 `raw/extracted/` 子目录，文件直接写进 `root` — 规避：测试中 output_dir 统一用 `root.join("raw/extracted")`。
[2026-06-20] TaskService 测试直接 `Queued -> Succeeded` 报 "Invalid state transition" — 根因：`validate_transition` 不允许跳过 Running 状态 — 规避：测试中插入 `transition_status(&t.id, TaskStatus::Running)` 再转 Succeeded。
[2026-06-20] 测试中模板路径 `src-tauri/templates/...` 在 cargo test 中找不到文件 — 根因：测试使用 `std::fs::read_to_string` 以 CWD 解析相对路径，CWD 可能不是 crate root — 规避：用 `env!("CARGO_MANIFEST_DIR")` 构建绝对路径。

[2026-06-20] cargo build 报 E0283 type annotations needed（疑云），定位在 BackendError::new("CODE", "msg".into(), true, true) 的第二参 —— 根因：BackendError::new 签名是 `message: impl Into<String>`，给 `&str` 再链 `.into()` 会让编译器无法推断目标类型（impl Into<String> 接收者 + `.into()` 返回类型双盲）—— 规避：`impl Into<String>`/`impl Into<...>` 形参**直接传 `&str`/String 字面量，不要再 `.into()`**（`&str: Into<String>` 已满足）。同理 &PathBuf/impl AsRef<Path> 等泛型形参也不要对实参多套一层 `.into()`。
[2026-06-20] 前端 Zustand selector 导致 Maximum update depth exceeded / "getSnapshot should be cached" 无限循环 —— 根因：`useStore(selectAllIssues)` 里 selector 每次 call `return [...local, ...deep]` 返回新数组引用，Zustand 默认 Object.is 比较 → 永远不等 → 每次 render 重渲 → React 触顶 —— 规避：selector 返回派生数组/对象时**不要**直接传 selector 进 hook，改成在组件里 `useMemo(() => [...localIssues, ...deepIssues], [localIssues, deepIssues])`（依赖项是 store 里两个稳定引用），或用 `useShallow`（zustand/react/shallow）做浅比较。
[2026-06-20] 测试 helper `fn write_file(context: &ProjectContext, ...)` 在多个 #[test] 里被传 owned `context`（来自 `let (context, root) = tmp_context()`）→ E0308，而 seed_clean_vault 里 context 已是 `&ProjectContext` —— 根因：同一 helper 被两种调用点用，借用规则不一致 —— 规避：统一**在 #[test] 调用点传 `&context`**（owned→引用），helper 内部 `context: &ProjectContext` 保持不变；seed_clean_vault 内部传 `context`（已是引用，自动再借一次 OK）。不要用 replace_all 把 `context,` 全替换成 `&context,`——会连带把 impl 方法里 `self.x(context, ...)`（context 已是 `&ProjectContext`）变成 `&&ProjectContext`，clippy needless_borrow 一片红。

[现象] 改了 trait 方法签名 `ProcessRunner::run_task_streaming` 的返回类型 `Result<(), _>` → `Result<String, _>`，`cargo build` 报「method has an incompatible type for trait」指向 `src-tauri/tests/task8_contracts.rs` 的 FakeProcessRunner 实现，而非真正的实现或调用点。
[根因] 改 trait 方法签名会级联到所有实现者，包括仅用于测试桩的 FakeProcessRunner；编译器报错指向桩，容易误以为只要改真实现就够。同时调用点（compile_commands 用 `?` 丢弃返回值）不会报错，造成「只有测试炸」的错觉。
[规避做法] 改 trait 方法返回类型时，全局搜该 trait 的所有 impl（含 tests/ 目录的桩），逐个同步签名；调用点用 `?` 丢弃返回值仍合法，但要在脑子里确认「丢弃是有意为之」而非忘了接。本次 chat 需要捕获 Agent stdout 作为答案文本，故改成 String，compile 主动丢弃——这是有意取舍。

[现象] `slice.iter().take_while(pred).rev().find(...)` 编译报 `the trait DoubleEndedIterator is not implemented for TakeWhile<...>`。
[根因] `TakeWhile` 不是 `DoubleEndedIterator`（无法从尾部反向，因为要从前缀判断），所以 `.rev()` 在它上面非法。`.iter().rev().take_while()` 顺序也不对（语义变了）。
[规避做法] 要在「截至某元素的切片」里反查最近一项：先 `let v: Vec<&T> = iter.take_while(pred).collect();` 再 `v.iter().rev().find(...)`。chat 的 save_answer_to_wiki 找「消息 id 之前最近的 user 轮」就是这个模式。

[现象] 任何 import 链路碰到 sigma.js（GraphView，进而 AppShell→App.test）的测试在 jsdom 下直接 ReferenceError: WebGL2RenderingContext is not defined，整个测试套件崩溃。
[根因] sigma.js 在模块加载期就引用 WebGL2RenderingContext / WebGLRenderingContext 做能力探测，jsdom 不提供这两个全局。
[规避做法] 在 src/test/setup.ts 顶部（任何 import 之前）给 globalThis 打 inert 桩：`WebGL2RenderingContext = class {}`、`WebGLRenderingContext = class {}`。真实 canvas 渲染另由 GraphView 的 try/catch 兜底（new Sigma 抛错时 setCanvasAvailable(false) 显示占位），桩只保证 import 不崩。

[现象] ForceAtlas2 在退化图（单个孤立节点、两个重合随机坐标点）上产出 NaN/Infinity 坐标，写回 .app/graph-cache.json 后下次加载节点位置变 null，sigma 渲染错乱。
[根因] Number(NaN) !== 0；JSON.stringify(NaN/Infinity) === "null"；缓存反序列化后 pos[0] 为 null 直接塞进 graphology 属性。
[规避做法] persistLayout 落盘前用 Number.isFinite 过滤，非有限值回退 0；读取缓存坐标处也保留兜底。任何把数值坐标序列化进持久层的路径都要做有限性校验。

[现象] 同一 Vitest 文件内后一个 React Testing Library 用例能查询到前一个用例的 DOM，出现重复按钮歧义。
[根因] Vitest 未启用 globals 时 Testing Library 未自动注册 cleanup；setup.ts 只加载 jest-dom matcher。
[规避做法] 在 src/test/setup.ts 显式 afterEach(cleanup)，保证每个用例卸载 React 树并清空 DOM。

[现象] Milkdown React 编辑器每次按键都丢光标、ProseMirror 重建闪烁，输入几乎不可用。
[根因] useEditor 的 deps 里挂了 live draft；store 在每次 markdownUpdated 回调里 setDraft，draft 变 → 父重渲染 → initialMarkdown 变 → useEditor deps 变 → 整个 Editor.make() 重建。

[现象] `Editor.make().use([commonmark, gfm, history, listener])` 报 "Type 'MilkdownPlugin[]' is not assignable to type 'MilkdownPlugin'"（对 commonmark/gfm/history 各报一次）。
[根因] `.use()` 签名是 `MilkdownPlugin | MilkdownPlugin[]`（一个插件或一个插件数组）；但 @milkdown/kit 导出的每个 preset（commonmark/gfm/history/listener）本身已经是 `MilkdownPlugin[]`。把它们再包一层 `[a, b, c, d]` 就成了 `MilkdownPlugin[][]`，数组元素类型不匹配。
[规避做法] 链式分别注册：`.use(commonmark).use(gfm).use(history).use(listener)`，每个调用吃一个 preset 数组，命中 `MilkdownPlugin[]` 重载。

[现象] react-markdown 把自定义 `wikilink://target` 链接的 href 清成空串，自定义 `a` 组件的 `href.startsWith(WIKILINK_SCHEME)` 判断永远 false，所有 wikilink 落到外链 fallback 分支（target=_blank）。
[根因] react-markdown v9 默认 `urlTransform`（`defaultUrlTransform`）只放行 http/https/mailto 等已知安全 scheme，未知 scheme 被剥离成 ""。

[现象] Rust 手写 frontmatter 解析器里 `let key = ...;` 在某分支 `entries.push((key.clone(), Scalar(...)))` 后循环末尾又 `entries.push((key, ...))`，编译报 "key moved twice / borrow after move"。
[根因] 同一个所有权变量在多个分支被消费；clone 掩盖一处，末尾再 move 必然报错。
[规避做法] 每轮迭代一次性算出 `(value, next_i)` 元组，循环体里 push 恰好一次；把 block-list 收集抽成 `collect_block_list(lines, start)` helper，避免在主循环里嵌套 push。解析器无外部 YAML 依赖（样本库只用 scalar + inline/block list），别为兼容性引 crate。

[现象] `chrono::Utc.timestamp_opt(sec, 0).map(...)` 编译报 LocalResult 没有 map。
[根因] `LocalResult<T>` 不是 Iterator/Option，没有 map；`timestamp_opt` 返回 `LocalResult<DateTime>`，需要转 Option。
[规避做法] 用 `.single()`（返回 Option<DateTime>）再 `.map(|dt| dt.to_rfc3339())`。chrono 新 API 一律走 timestamp_opt + .single()，别再碰已弃用的 `.timestamp()`（panic 风险）。

[现象] 前端乐观并发保存：后端写盘成功但紧跟的 read_wiki_page 失败时，store 把 saveState 标成 "error"，用户以为没存；或用户保存中途点开另一页，保存回调的 set({page: refreshed}) 覆盖了新打开的页面。
[根因] 把"保存"和"重读刷新"耦合在同一个 try/catch；重读失败回退到 error 状态；未捕获保存期间的导航事件。
[规避做法] 写盘成功后单独 try/catch 包住重读：重读失败→仍 saveState "saved"（不掩盖成功）；应用 refreshed 前判 `stillViewing = selectedPath === null || === savedPath`，只有用户没导航到别的页才覆盖。expectedHash 取自当前 page.meta.hash，None→CreateNew，Some→OverwriteIfHashMatches，FILE_HASH_MISMATCH→saveState "conflict"。

======================================================================
serde tagged enum `#[serde(tag="kind")]` 不 camelCase 结构变体字段 — `rename_all` 作用在 enum 的变体名上，不会渗透到 struct-variant 内部字段，导致嵌套 `pending_action` 等字段以 snake_case 外泄，前端 TS 类型对不上 — 改用「struct + `kind` 鉴别字段」结构体，并在 struct 上单独加 `#[serde(rename_all="camelCase")]`，避免在 enum 上依赖 rename_all 渗透。
`Err(...).with_details(...)` 闭包缺右括号导致 "mismatched closing delimiter" — 写多行 `return Err(BackendError::new(...).with_details(...));` 时容易漏掉最外层 `Err(` 的闭合 `)`，rustc 报「unclosed delimiter / mismatched closing delimiter」且行号指向文件末尾 — 计数好 `Err(` 的层数，`}));` 不够就补成 `})))`。
`include_str!` 模板路径在 Windows 上以 `CARGO_MANIFEST_DIR` 为基准 — 模板必须放在 `src-tauri/templates/...` 并用 `../../templates/...` 相对路径，移动目录时要同步改 include 路径，否则编译期报文件找不到。
提取 HTML 标题时切片索引偏移错误 — `extract_html_title` 用 lowercased 字符串定位 `<title>` 后，原字符串的索引偏移需要逐字精确计算：`after_tag` 包含 `>` 时，`content_start` 已跳过 `>`，但后续搜索 `</title>` 的 `tag_rest` 仍以 `>` 开头，导致 `end` 多计 1 个字符，标题末尾附带 `<` — 跳过 `>` 后再搜索 `</title>`，保证 content 切片不包含标签字符。包含属性的标题 (`<title lang="en">`) 同理需要在 `after_tag.find('>')` 后 +1 跳过 `>`。

`cargo test` 默认联网解析依赖在本机超时 — 依赖已缓存时加 `--offline` 即可跑通全套测试；不要把「联网超时」误判成「代码失败」。

`#[derive(Default)]` 与手写 `impl Default` 不能共存 — 当某个字段类型（如 `NotificationService`）无法 derive Default 时，需要对整个 struct 手写 `impl Default`，此时必须删除 struct 上的 `#[derive(Default)]`，否则报 E0119 conflicting implementations。

现象 — 模型在 ```html 围栏文档（或无围栏裸 HTML）后追加一行「Explanation: I generated…」散文，导致导出的 .html 末尾混入非 HTML 文本，iframe 预览和文件都不干净。 — 根因 — SKILL.md 虽要求「只输出文档」，但模型（尤其 BYOK）经常在闭合 `</html>` 后补一句解释；extract_html 只剥围栏不处理尾随散文。 — 规避做法 — extract_html 在剥围栏后调用 trim_trailing_prose：rfind 最后一个 `</html>`（**case-insensitive**，用 to_ascii_lowercase，因为模型常输出 `</HTML>`），保留到并含该标签为止；找不到闭合标签则原样返回（绝不盲目截断合法内容）。已在 export_service.rs 单测覆盖 fenced+prose、bare+prose、case-insensitive 闭合三种形态。
现象 — ProjectReport（项目级报告）传入的 sourcePath 被用作 slug，历史列表里的项目报告文件名被命名成某个单页名（如 `agent-20260620-...`），与「整库报告」语义矛盾、易误导。 — 根因 — build_output_relative_path 对所有类型都用 source_path 做 slug，未区分项目级类型。 — 规避做法 — ExportType::requires_source() 区分单页/项目级；build_output_relative_path 对 ProjectReport **忽略 source_path**，slug 回退为 skill folder 名去 `html-` 前缀（`project-report`）。单测 build_output_relative_path_ignores_source_for_project_report 断言路径不含源页名。
现象 — cargo build --tests 报 `this function takes 3 arguments but 2 arguments were supplied` 指向 ExportService::build_output_relative_path。 — 根因 — 该方法是 `&self`（持有 FileStore），不是关联函数，测试里写成 `ExportService::build_output_relative_path(...)` 漏了 receiver。 — 规避做法 — 测试里先 `let service = ExportService::default();` 再 `service.build_output_relative_path(...)`。同类 `&self` 方法（build_export_prompt/write_html/append_record/list_records）同此。
现象 — ESLint/TS 在 AppShell 的通用 else 分支 `t(\`view.${activeView}.paneTitle\`)` 报错，因为新增 exports 分支后 activeView 被收窄为 `never`（全 9 个 AppView case 都已显式分支）。 — 根因 — TypeScript 穷尽性检查：union 在所有 case 处理后剩 never，模板串里的属性访问类型不匹配。 — 规避做法 — 通用兜底分支里 cast `activeView as string`（该分支现已不可达，仅作防御）。或干脆移除兜底分支（若确认 union 已穷尽）。
