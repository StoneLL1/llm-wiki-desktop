# Codex Goals 指南

## 概述

Goals 是 [[openai-codex]] 的持久目标机制。与一次性 prompt 不同，Goals 给 Codex 一个持续有效的完成条件：任务什么时候算做完、怎么验证、过程中什么不能动。从 Codex 0.128.0 开始支持（目前仅 codex cli）。

Goals 针对的是另一类任务：**下一步该怎么做，取决于上一步发现了什么**。比如性能调优、不稳定测试排查、依赖迁移、需要复现的 bug、多步重构、基于 benchmark 的调参，或需要产出最终文档的研究任务。

## Goals vs 普通 Prompt

| 维度 | 普通 Prompt | Goals |
|------|------------|-------|
| 执行模式 | 说做→做→汇报→等 | 做→检查→继续或完成 |
| 目标持续性 | 一次性 | 持久附在线程上 |
| 完成判断 | 用户判断 | 基于证据对照检查 |
| 继续条件 | 无 | 目标激活 + 在预算内 + 线程空闲 |

## 好的 Goal 怎么写

强 Goal 定义六件事：

1. **结果** — 工作完成时应该是什么状态
2. **验证方法** — 用什么来证明（测试、benchmark、报告、命令输出）
3. **约束** — 工作期间什么不能退化
4. **边界** — 可以用哪些文件、工具、数据、仓库或资源
5. **迭代策略** — 每次尝试后怎么决定下一步
6. **阻塞停止条件** — 什么时候该停下来报告

## Goal 激活后的三件事

1. **目标持续可见** — 跑了测试失败了，线程里还有原始目标；benchmark 提升但没过阈值，可以继续
2. **从空闲线程继续** — 不在另一轮还在跑时继续，不在用户输入排队时继续，只在空闲+激活+预算内时继续
3. **完成必须有证据** — 不因模型觉得"大概差不多了"就标记完成，只有把目标和具体证据对照检查后才能标完成

## Kundel 的 7 条 Goal 原则（类比 OKR）

OpenAI 的 dominik kundel 在 2026-06 分享了 /goal 使用指南，类比职场管理中的 OKR 方法论^[raw/articles/2026-06-05-codex-goal-command-guide.md]：

| # | 原则 | 核心要点 |
|---|------|----------|
| 1 | 目标要能验收、用数字量化 | prompt 不只是任务描述，更是退出标准。带数字的比虚的清楚得多：「构建时间减少 30%」vs「优化一下性能」 |
| 2 | 多给上下文信息 | 直接告诉它瓶颈在哪、能用哪些工具、哪儿容易踩坑。或先用 plan mode 调研输出 plan.md 再给 goal 参考 |
| 3 | 让进度可衡量 | 有些任务天然可度量（构建时间、测试覆盖率），其他的得一起想，如写截图 diff 工具或搭 eval 套件。防假达标：它可能靠删测试达到 100% 通过 |
| 4 | 接近生产的真实环境 | 预览环境砍了部分构建路径会导致数据对不上，必须摸得到跟生产同栈同 flag 的测试环境。有人甚至挂真机抓 profiling |
| 5 | 视觉类目标要格外小心 | 「像素级一致」容易让 Agent 钻进某个图标的牛角尖。更稳：把图当参考背景，验收换成 feature 清单或 spec |
| 6 | 长任务做好过程跟踪 | 关键节点 commit + draft PR + 预览部署；进度写进 markdown/HTML 文件；重要进展 post 到 Slack；用 /side 开分支问状态不中断主线 |
| 7 | 完成后复盘清理 | /goal 不撞墙不回头，过程里塞了一堆没跑通或半截作废的尝试。先 /review 再清理失败路径留下的文件，别跟着一起交付 |

鲁工评价：/goal 在 [[openai-codex]] 的 App、IDE 插件、CLI 三端都能用，且 [[claude-code]] 推出类似功能更早，用法相近。在 yolo 模式下结合 /goal 能一次性完成大部分场景的不同任务。

## 内部架构设计

- Goal 是**持久化的线程状态**，不是全局记忆，也不是项目级指令
- Goal 属于有相关上下文的那个线程（文件、命令、diff、日志、推理链）
- 继续是**事件驱动**的，不是简单循环——只在安全边界处检查
- 调度器行为保守：纯规划不触发继续，被打断会暂停目标，无工具调用的继续会抑制下一次
- 预算处理明确：达上限时停止工作，汇总进度和阻塞点

## 什么时候不该用 Goals

- 一行代码的修改、简单解释、短小代码评审 → 用普通 prompt
- 终点线模糊（"把这个做得更好"）→ 不适合 Goal
- 掩盖不确定性 → 在 Goal 里说清楚数据可能不可用
- Goals 最有力的三个条件同时具备：持久目标 + 基于证据的完成线 + 路径可能需要多轮调查
