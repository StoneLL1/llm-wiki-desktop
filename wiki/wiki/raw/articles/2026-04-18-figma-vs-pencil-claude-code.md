# Figma vs. Pencil，谁才是Claude Code的最佳Vibe Design工具


**作者**: AI编程实验室

大家好，我是鲁工。
上周写了一篇关于DESIGN.md的文章，聊的是怎么用一个设计规范文件让Claude Code生成的前端UI不那么丑。那篇发出来之后，有读者认为，
DESIGN.md就相当于给项目换个皮肤，一点也不优雅。
Vibe Design来了！通过DESIGN.md搞定前端UI设计
那么，除了DESIGN.md这种文本约束，有没有办法让Claude Code直接跟设计工具打通？
那必须有。DESIGN.md确实管用，但它本质上还是在用文字描述设计意图，AI拿到的是语义信息，不是结构化的设计数据。这就像你跟装修工人说"客厅要简约风"，和直接给他一张施工图纸，效果肯定不一样。
顺着这个思路，我最近重点研究了两个方向：一个是Figma通过MCP Server接入Claude Code，另一个是一个叫Pencil的新工具，天生就是为AI编码环境设计的。这两个工具走的路线完全不同，但目标一样，都是想把设计环节塞进Vibe Coding的工作流里。
这篇我就来聊聊，这两条路各自是什么体验，适合什么人。
Vibe Coding的设计断裂
用Claude Code做全栈开发的朋友应该都有体会，代码逻辑这块AI越来越靠谱了，但前端UI这块始终不那么可控，Vibe出来的落地页一直被用户所诟病。
原因其实很简单。Claude Code读得懂你的代码结构，读得懂你的API接口，读得懂你的数据库Schema，但它读不懂你脑子里想要的那个界面长什么样。你说"做一个简洁的登录页"，它能给你生成一个功能完整的登录页，但配色、间距、组件风格，全靠AI自由发挥。运气好像那么回事，运气差就是一言难尽。
这个问题的根源在于，设计信息和代码信息之间有一条鸿沟。传统工作流里，这条鸿沟靠前端工程师人肉搬运来填，看着设计稿一个像素一个像素地对。Vibe Coding把这个人肉搬运环节干掉了，但鸿沟还在那里。
所以现在社区里出现了两种解题思路。
一种是让AI能直接读取设计工具里的结构化数据，Figma走的就是这条路，通过MCP Server把设计上下文喂给Claude Code。另一种更激进，干脆让设计文件和代码住在同一个仓库里，共享同一套Git工作流，Pencil走的是这条路。
这两条路线和工具我都做了一些实践尝试，今天就简单说一下这个事。
Figma路线：设计中枢向代码延伸
Figma很多人都听过，UI设计领域的绝对头部工具。过去两年Figma密集地往AI方向发力，2025年推出了Figma Make（用自然语言直接生成UI布局和交互原型），同年6月发布了Figma MCP Server的beta版，到2025年底的Schema大会上正式GA。
Figma接入Claude Code的核心链路是这样的：Figma MCP Server作为桥梁，让Claude Code能直接读取Figma文件里的设计数据（组件结构、变量绑定、自动布局参数），拿到的是结构化的JSON，不是截图。然后Claude Code基于这些数据生成代码，生成完还能反向写回Figma画布。
这里面有个关键的东西叫Code Connect。简单来说就是把Figma里的设计组件和你代码仓库里的真实组件做映射。比如Figma里有个PrimaryButton组件，Code Connect会告诉Claude Code：这个东西在代码里对应的是src/components/Button.tsx，用的是这些props。这样AI生成代码的时候就不会凭空捏造组件，而是直接调用你仓库里现成的。
部署上，Figma提供两种MCP Server模式。一种是Remote Server（云端），通过
https://mcp.figma.com/mcp
连接，支持双向读写，官方推荐用这个。另一种是Desktop Server，走本地桌面应用，适合有数据隔离需求的团队。
听起来挺完美的，但实际用下来，有一些需要注意的地方。
Figma的设计文件天然包含大量视觉元数据，阴影参数、隐藏图层、未组件化的散落路径，这些对代码生成来说都是噪音。根据社区里的实战反馈，一个稍微复杂点的Figma页面，MCP Server返回的JSON载荷能达到5MB以上。这个体积对大模型的上下文窗口是很大的压力，AI的注意力会被这些无关信息分散，代码生成的准确率也会打折扣。
所以走Figma路线有个前提条件：你的Figma文件得足够规范。所有布局必须用Auto Layout，不能有随意拖拽的绝对定位元素。颜色、字号、间距都得绑定设计变量（Design Tokens），不能硬编码。图层命名要语义化，不能留着"Frame 123""Rectangle 45"这种默认名。
总结一下就是，Figma MCP Server能发挥多大威力，取决于你的Figma文件有多"工程化"。文件规范的团队用起来效果很好，文件混乱的话AI拿到的也是一堆噪音。
我这里用Figma出一个户外运动商城的落地页面设计，然后在Claude Code中通过Figma MCP访问该设计稿，就可以很好的在项目中一比一复现该设计。

Pencil路线：代码仓库就是设计文件
Pencil（
pencil.dev
）是一个相对新的工具，感觉也是最近几个月才火了起来。我很早就把Pencil加入了写作选题，但一直拖了好久才开始。
Pencil的理念跟Figma完全反过来。Figma的逻辑是"设计在云端，向代码延伸"。Pencil的逻辑是"设计文件直接住在代码仓库里，跟代码共享Git的一切"。
具体来说，Pencil用一种叫.pen的开放文件格式存储设计数据。这个格式底层是JSON结构，版本控制友好，可以直接git diff看到设计改了什么。.pen文件放在你的项目目录里，跟src、package.json平级，设计和代码物理上就在一起。
这意味着什么呢？你在Pencil画布上拖一个组件、改一个颜色，本质上就是修改了仓库里的一个JSON文件。这个修改会被Git追踪，可以提交、回滚、创建分支、发PR、做Code Review。设计变更和代码变更走完全一样的工程化流程。
Pencil的AI能力直接依赖Claude Code。安装Pencil之后，本地最好能有Claude Code等Coding Agent工具，Pencil的AI功能走的就是Claude的能力。Pencil自带一个本地MCP Server，设计数据不会发到云端（只有AI prompt会发给Claude），隐私方面相对可控。

MCP提供了一组很实用的工具函数。batch_design可以让AI批量创建、修改、删除界面元素。get_screenshot能在后台渲染当前设计的预览图，让AI用视觉能力做UI还原度自检。snapshot_layout能分析盒模型布局结构，检测元素重叠和定位异常。get_variables和set_variables可以读写设计变量，跟CSS变量双向同步。
还有一个挺有意思的功能，Pencil支持同时跑最多6个AI Agent在画布上并行工作，社区的叫法是"AI Multiplayer"。你可以让几个Agent同时探索不同的设计方向，然后挑一个最好的。

核心对比：两个完全不同的产品
研究完这两个工具，我最大的感受是：它们根本不是同一类东西，只是恰好都在解决"设计到代码"这个问题。
如果用人来类比的话，Figma像一个经验丰富的建筑设计院。有完整的设计规范体系，有多人协作的工作台，有从草图到施工图的全流程管理。你要盖一栋大楼，找它没错。但它的图纸格式是自己的专有标准，施工队拿到图纸还得做一道翻译，翻译质量取决于图纸画得多规范。
Pencil更像一个直接住在工地上的技术型包工头。它不画传统意义上的设计图，而是直接在你的代码仓库里用一种施工队能直接读懂的格式描述"这面墙放哪、这扇窗多大"。没有翻译环节，设计就是代码的一部分。代价就是，别指望它帮你做那种异形建筑或者艺术装置。
聊到这儿，其实结论已经比较清楚了。这两个工具适合完全不同的场景和人群。
如果你是独立开发者或者工程师主导的小团队
，没有专职设计师，主要靠Vibe Coding搞定全栈，Pencil是更自然的选择。.pen文件直接在仓库里，Git天然管理版本，AI代码生成的稳定性也更好，加上目前免费，试错成本极低。
所以从这一点来看，我其实更喜欢Pencil。
如果你的团队有设计师，或者已经建立了成熟的Figma设计系统
，那Figma MCP Server是更务实的选择。不需要推翻现有工作流，在已有的Figma资产基础上加一层MCP桥接就行。但前提是，Figma文件得做工程化规范，Auto Layout全覆盖，变量绑定到位，图层命名语义化。文件越规范，AI产出越靠谱。
混合路线也值得考虑。
社区里有一些全栈工程师的做法是：在Pencil和Claude Code里快速搭骨架和跑通逻辑，然后把初步成果导入Figma做最终的视觉打磨和团队协作。这种两头都用的方式对个人能力要求比较高，但确实能发挥两边的长处。
还有一点我觉得值得提的。DESIGN.md这种纯文本约束和MCP这种结构化数据接入，并不是互相替代的关系。DESIGN.md管的是宏观的设计规范（品牌色、间距体系、排版规则），MCP管的是具体的组件结构和布局数据。两者配合起来效果更好。
最后再补一句。Vibe Design这个方向还相对早期，Figma MCP Server才GA不到半年，Pencil更是刚出来的新工具。两边都在快速迭代，现在的体验不代表三个月后的体验。
我的建议是，如果你在用Claude Code做前端，两个都值得花一两个小时试一下，亲手感受一下差异，比看任何评测文章都来得直接。
