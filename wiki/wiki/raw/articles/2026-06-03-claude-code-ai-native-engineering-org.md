# Claude Code 团队实践：智能体编程如何重塑工程组织与流程

**作者**: Fiona Fung (Director of Engineering, Claude Code & Claude Cowork) | **来源**: Claude Blog
**活动**: Code w/ Claude SF 2026 | **阅读时间**: 5 分钟

## 核心背景

> 「多年来，工程带宽是构建应用最昂贵的部分。我们过去围绕软件规划和交付的每一个流程——先瀑布再敏捷——都建立在这个成本之上。」
> 「在 Claude Code 团队，写代码、写测试、重构很少再拖慢我们了。但瓶颈并没有随着 agentic coding 消失了——验证、代码审查和安全取而代之。」

- 自采用 agentic coding 为默认工作方式后，**编写代码的成本崩塌式下降**，但新瓶颈出现
- 其他工程领导者最常问：「人类怎么跟得上你们的代码审查速度？」

## 四大流程变革

### 1. 规划 → 即时（JIT）路线图

| 之前 | 之后 |
|------|------|
| 花大量时间预规划（如六个月路线图），因为编码时间贵 | JIT 规划：快速原型 → 让内部用户用上 → 根据反馈行动 |
| 设计文档 | PR 或原型中的讨论 |

> 「我们写了一份相当不错的六个月路线图，然后因为 Claude Code，太多事情变了，第三个月就过时了。」

### 2. 上下文收集 → 先问 Claude，不找作者

| 之前 | 之后 |
|------|------|
| 找到写代码的人问答案 | 直接问 Claude（如「谁导致了这个回归？」「这个决策的理由是什么？」） |
| - | 永远追问：「有办法自动化吗？」 |

**案例**: 让 Claude 每天早上自动汇总客户反馈渠道——从作者手动喝咖啡时做的事变成后台自动运行。

### 3. 代码审查 → 信任但验证，人类专注专业判断

| 之前 | 之后 |
|------|------|
| 人类审查一切 | Claude 处理所有风格、Lint、PR 反馈、Bug 捕获、提交前修复、测试添加 |
| - | 人类只在专业领域审查：法律审查、信任边界/安全代码、产品品味 |

> 「持续评估很重要，因为信任与验证的正确平衡会随着模型改进而变化。今天需要人类做的事，下一个模型可能就不同了。」

### 4. 团队构成 → 角色模糊化，两类人才

**之前**: 固定角色——工程师写代码、PM 规划、设计师设计

**之后**: 
- PM 大量编码（「非传统编码者」能做更多工程工作）
- 工程师接手内容、设计等传统非技术工作

**招聘重点两类人**:
1. **有产品感的创造性建设者** — 「梦想家，深度好奇、热衷于交付解决问题的产品」
2. **有深层系统专业知识的工程师** — 构建 Claude Code on the Web 等产品时不可或缺

> 「我更少关注原始吞吐量；模型处理这些。更重要的问题是哪里还需要人类专业知识，那才是我关注的重点。」

## 他们如何推广新规范

**自上而下的原则（不可协商的「必须做」）**:
- **无情地吃自己的狗粮** — 每个团队成员（含跨职能伙伴）都使用 Claude Code 和 Claude Cowork
- **保持团队尽量扁平** — 每个经理首先是 IC，亲自写真实代码

## 总结

工程瓶颈从「写代码」转向「验证、审查、安全」。新范式下最重要的是识别**哪里还需要人类专业判断**，而不是比拼编码速度。
