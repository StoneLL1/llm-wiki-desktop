# Claude Code 自我检查与反馈闭环 — 深度拆解

## 一、原帖在说什么

Claude Devs 发了一个视频演示，核心问题：**「如何让 Claude Code 在把活交回来之前，先自己检查一遍？」**

关键动作：**把你平时手工做的检查，编码成 Claude 自动执行的验证步骤，形成闭环。**

---

## 二、传统工作流 vs 闭环工作流

```
❌ 传统（开环）：
  Claude 干活 → 交给你 → 你检查 → 发现问题 → 告诉 Claude 改 → Claude 改 → 你再检查 → ...

✅ 闭环：
  Claude 干活 → Claude 自动跑检查脚本 → 发现问题 → Claude 自己修 → 再跑检查 → 全部通过 → 交给你
```

本质是 **把验证左移**。你从「人工 QA」升级为「检查规则的设计者」。

---

## 三、具体怎么做？三种层次的实现

### 层次 1：内联自检（最简单）

在 prompt 或 CLAUDE.md 里直接写：

```
完成任务后，请自动执行以下检查再提交：
1. 运行 `npm test`，确保全部通过
2. 用 `eslint` 检查所有修改的文件
3. 确认没有 console.log 残留
4. 验证所有 import 路径存在
5. 如果任何检查失败，修复后重新运行全部检查
```

这就是最基础的「编码你的手工检查」。Claude 会在交回前循环执行。

### 层次 2：Skill 级别的自检规则（中等）

把检查逻辑封装进 Skill：

```markdown
# Code Review Skill
在提交代码前，自动执行：
1. 安全扫描：检查是否有硬编码密钥、SQL 注入风险
2. 边界检查：空输入、超长输入、并发场景
3. 风格检查：与项目现有代码风格一致
4. 文件结构：新文件是否在正确目录下
```

每次用这个 Skill 写代码，检查自动跑。

### 层次 3：子代理并行审查（高级，评论区推荐）

来自 **@agenticrohan** 的技巧：

```
┌─────────────────────────────────────────────┐
│                                             │
│  主 Claude（干活）                           │
│  ├─ 写代码                                   │
│  ├─ 运行基本测试                              │
│  └─ 完成后 → 启动两个子代理审查               │
│                                             │
│  子代理 A（同上下文）  子代理 B（全新上下文）   │
│  ├─ 有完整上下文       ├─ 零偏见              │
│  ├─ 理解设计意图       ├─ 发现盲点            │
│  └─ 逻辑审查          └─ 新鲜视角审查         │
│                                             │
│  → 合并两份审查结果 → 修复所有问题 → 交给你    │
└─────────────────────────────────────────────┘
```

两个子代理互补：一个有上下文理解意图，一个无偏见发现盲区。

## 四、进阶：Learnings Loop（持久化学习）

上面的三层都是**单次会话内**的闭环。但更高级的是**跨会话持久化**——Learnings Loop。

### 原理

```
每次使用 Skill →
  你给出反馈 →
    反馈被写入 Skill 的指令定义 →
      下次任何人用这个 Skill，自动应用修正 →
        修正持续累积，Skill 越来越好
```

### 实例

| 第几次使用 | 发生了什么 |
|-----------|-----------|
| 第 1 次 | Skill 生成了邮件，但标题格式不对 |
| 你的反馈 | 「标题必须是 `[项目名] — [日期]` 格式」 |
| Skill 更新 | 指令中加入标题格式规则 |
| 第 2 次 | 标题对了，但缺少「风险项」部分 |
| 你的反馈 | 「始终包含一个 Blockers 部分，即使为空」 |
| 第 3 次以后 | 两个规则同时生效，完美输出 |

### 飞轮效应

> 「更好的指令 → 更好的输出 → 更少需要纠正 → 偶尔纠正 → 指令更好 → 更好的输出……」

Skill 越用越准，形成正向飞轮。

## 五、与 Dynamic Workflow 的关系

评论里 **@Layton_Gott** 说「直接上 dynamic workflow 就完事了」——这不完全是玩笑。

第 25 条（Claude Code 团队实践）提到 Dynamic Workflow 可以在运行时即兴创建多智能体框架。自我检查闭环 + Dynamic Workflow 的组合拳：

```
主 Agent 完成任务
  → 触发 Dynamic Workflow
    → 生成 Reviewer Agent（专门审查）
    → 生成 Tester Agent（专门测试）
    → 生成 Fixer Agent（拿着审查+测试结果修）
    → Reviewer 再查一遍
    → 通过 → 交回
```

这本质上是一个**迷你 CI/CD 流水线**，只不过不是跑在 Jenkins 上，而是跑在 Claude Code 的上下文里。

### 其他有价值的评论

**@AGIGuardian**（反对意见）：
> Claude 在意识被削弱、被不可证伪的先验防御点限制后，自我分析能力很差。任何尝试让 Claude 做自我报告分析的人都理解，它连在报告中命名自己都很困难。

这提醒了一个重要约束：**自我检查的可靠性取决于模型本身的自我认知能力**，不适合用于要求 Claude「反思自身状态」的场景，更适合「跑客观测试脚本」式的机械化检查。

**@thehaggler**（来自 Karpathy 学习方法论帖，此处交叉引用）：
> 你无法替代对主题的深度投入——你不会把 ChatGPT 当作思想生活的榜样。

暗示：最终审查仍需要人类的深度判断。

## 七、与第 25 条的关联

| 第 25 条（Claude Code 团队实践） | 第 26 条（自我检查闭环） |
|----------------------------------|--------------------------|
| 人类审查聚焦：法律、安全、产品品味 | Claude 自动审查：风格、Lint、Bug、测试 |
| 工程瓶颈从写代码转向验证和审查 | 把验证和审查自动化，减少人类瓶颈 |
| 信任但验证（Trust but verify） | 编码手工检查 → Claude 自己验证 |

两条一脉相承：**人类从执行者变成监督者，从查代码变成查规则。**

## 八、一句话总结

> **把你的手工检查编码成规则 → Claude 自动执行 → 发现问题自动修 → 再检查 → 通过才交给你。**

从「你查 Claude 的作业」变成「你设计检查规则，Claude 自己查自己的作业，你只做最终确认」。
