总结一下这些资料里关于 Agent Memory 的主要观点，特别是不同方案的取舍。

AI
claude14:30ingest · 3 来源

根据当前 Wiki 的 4 个相关页面，Agent Memory 的核心张力在于广度 vs 结构化程度。

主流实现可以归为四类：

1. 短上下文窗口 — 把最近内容直接保留在 LLM 上下文里。零额外组件，但成本随长度线性上升。

2. 长上下文检索（RAG） — 把资料存到向量库，提问时检索注入。可覆盖百万级文档，但每次只能"瞥见"若干片段1。

3. 外部记忆系统 — MemGPT、LangGraph State 等把记忆从模型中剥离，单独管理。能跨会话保留，但需要复杂的遗忘策略2。

4. 多模态记忆 — 视觉 / 音频模态经专门编码器嵌入到统一空间。

取舍维度：覆盖广度、结构化程度、可维护性。LLM Wiki 模式（本应用所采用的）属于 预先结构化 路线 — 把资料编译成稳定 Markdown，而不是即时拼接。

那 LLM Wiki 模式相比 RAG，最大的代价是什么？

AI
claude14:31ingest · 2 来源

核心代价是预先编译成本。

RAG 在提问时即时检索，零预处理；LLM Wiki 需要在导入资料后触发编译，由 Agent 把原始资料整理成结构化页面。这意味着：

• 首次导入需要等待编译完成（通常几十秒到几分钟）；
• 资料更新后需要重新编译相关页面；
• 编译质量受 Agent / Schema 影响，需要 Lint 维护。

换来的是：稳定可读的页面、可被外部编辑器修改、可被 Git 跟踪、问答时上下文更精准3。详见 wiki/concepts/rag.md 中的对比段。

3 Retrieval Augmented Generation wiki/concepts/rag.md

对于跨会话长期项目，LLM Wiki + 外部记忆 的组合最稳。

原因有三：

1. LLM Wiki 沉淀了结构化、可审计的知识资产；
2. 外部记忆（如 Letta、LangGraph）承载会话级状态；
3. 二者通过 wikilinks 关联，可在 Chat 中即时唤起。4
